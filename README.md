# Домашнее задание к занятию «Компоненты Kubernetes»

## Задание

Необходимо рассчитать требования к Kubernetes-кластеру для проекта.

В проекте есть:

- база данных;
- кеш;
- frontend;
- backend.

Также необходимо учесть служебные ресурсы Kubernetes и предусмотреть отказ как минимум одной worker-ноды.

---

## 1. Расчёт ресурсов приложения

### База данных

Для одного экземпляра требуется:

- 1 CPU;
- 4 ГБ RAM.

Необходимо 3 экземпляра:

```text
CPU: 1 × 3 = 3 CPU
RAM: 4 × 3 = 12 ГБ
```

Итого для базы данных:

```text
3 CPU
12 ГБ RAM
```

### Кеш

Для одного экземпляра требуется:

- 1 CPU;
- 4 ГБ RAM.

Необходимо 3 экземпляра:

```text
CPU: 1 × 3 = 3 CPU
RAM: 4 × 3 = 12 ГБ
```

Итого для кеша:

```text
3 CPU
12 ГБ RAM
```

### Frontend

Для одного экземпляра требуется:

- 0.2 CPU;
- 50 МБ RAM.

Необходимо 5 экземпляров:

```text
CPU: 0.2 × 5 = 1 CPU
RAM: 50 × 5 = 250 МБ
```

Итого для frontend:

```text
1 CPU
250 МБ RAM
```

### Backend

Для одного экземпляра требуется:

- 1 CPU;
- 600 МБ RAM.

Необходимо 10 экземпляров:

```text
CPU: 1 × 10 = 10 CPU
RAM: 600 × 10 = 6000 МБ ≈ 6 ГБ
```

Итого для backend:

```text
10 CPU
6 ГБ RAM
```

## 3. Расчёт worker-нод

Для worker-ноды я выбрал следующую конфигурацию:

```text
8 vCPU
16 ГБ RAM
```

При этом нельзя отдавать все ресурсы ноды приложениям, так как на ней также работают операционная система, kubelet, container runtime, CNI и другие служебные компоненты Kubernetes.

Для учебного расчёта резервирую на каждой worker-ноде:

```text
1 CPU
1 ГБ RAM
```

Тогда для Pod остаётся примерно:

```text
7 CPU
15 ГБ RAM
```

### Проверка варианта с тремя worker-нодами

Три ноды физически дают:

```text
3 × 8 CPU = 24 CPU
3 × 16 ГБ = 48 ГБ RAM
```

Но по условию кластер должен пережить отказ минимум одной ноды.

После отказа одной из трёх нод останется всего:

```text
2 × 8 CPU = 16 CPU
2 × 16 ГБ = 32 ГБ RAM
```

Приложению требуется 17 CPU.

Следовательно, даже без учёта служебных ресурсов:

```text
16 CPU < 17 CPU
```

Трёх worker-нод недостаточно.

---

## 4. Вариант с четырьмя worker-нодами

Четыре worker-ноды дают:

```text
4 × 8 CPU = 32 CPU
4 × 16 ГБ = 64 ГБ RAM
```

Если учитывать принятый резерв по 1 CPU и 1 ГБ RAM на каждой ноде, для приложений остаётся примерно:

```text
4 × 7 CPU = 28 CPU
4 × 15 ГБ = 60 ГБ RAM
```

Это больше требуемых:

```text
17 CPU
30.25 ГБ RAM
```

### Отказ одной worker-ноды

Если одна worker-нода выходит из строя, остаются три:

```text
3 × 8 CPU = 24 CPU
3 × 16 ГБ = 48 ГБ RAM
```

С учётом служебного резерва:

```text
3 × 7 CPU = 21 CPU
3 × 15 ГБ = 45 ГБ RAM
```

Сравниваю с нагрузкой приложения:

```text
Требуется: 17 CPU / 30.25 ГБ RAM
Доступно:  21 CPU / 45 ГБ RAM
```

После отказа одной worker-ноды остаётся запас:

```text
CPU: 21 - 17 = 4 CPU
RAM: 45 - 30.25 = 14.75 ГБ
```

Поэтому для проекта выбираю:

```text
4 worker-ноды
8 vCPU / 16 ГБ RAM каждая
```

---

## 5. Отказоустойчивость базы данных и кеша

У базы данных и кеша по три экземпляра.

Их необходимо размещать на разных worker-нодах, чтобы выход из строя одной ноды не привёл к потере сразу нескольких реплик одного сервиса.

Например:

```text
worker-1
├── DB-1
└── Cache-1

worker-2
├── DB-2
└── Cache-2

worker-3
├── DB-3
└── Cache-3

worker-4
└── frontend/backend
```

На практике для такого распределения можно использовать anti-affinity или topology spread constraints.

Frontend и backend могут распределяться scheduler Kubernetes между всеми доступными worker-нодами.

Выбираю:

```text
3 control-plane ноды
```

```text

```

Три control-plane ноды позволяют не делать управление кластером зависимым от одной машины.

## 7. Итоговая конфигурация кластера

Получается следующая схема:

```text
Kubernetes cluster
│
├── Control Plane
│   │
│   ├── control-1
│   │   └── 2 vCPU / 4 ГБ RAM
│   │
│   ├── control-2
│   │   └── 2 vCPU / 4 ГБ RAM
│   │
│   └── control-3
│       └── 2 vCPU / 4 ГБ RAM
│
└── Worker Nodes
    │
    ├── worker-1
    │   └── 8 vCPU / 16 ГБ RAM
    │
    ├── worker-2
    │   └── 8 vCPU / 16 ГБ RAM
    │
    ├── worker-3
    │   └── 8 vCPU / 16 ГБ RAM
    │
    └── worker-4
        └── 8 vCPU / 16 ГБ RAM
```

Таким образом, выбранная конфигурация выдерживает выход из строя одной worker-ноды и сохраняет достаточно ресурсов для запуска всех компонентов приложения.

Размер дискового пространства отдельно не рассчитывал, потому что в условии не указан объём базы данных, кеша и необходимого постоянного хранилища.

Приложение для разных окружений можно упаковать в Helm-чарт, а параметры окружений и ресурсов задавать через отдельные `values.yaml`.
